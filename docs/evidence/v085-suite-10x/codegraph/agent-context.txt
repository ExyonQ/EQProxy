So the origin socket, and any `listen(backlog)` applied to it, live in `start_keepalive_origin` (`nodes:\`6a19d942-9602-e8a7-11fd-2b6cd11c4912\``), a helper in the same file that returns `(SocketAddr, Arc<Atomic…>, …)` counters. That is the function to open first; it is the only place the origin listener is constructed for this test.

**Why the backlog is load-bearing here.** The test drives 400 concurrent streams over 4 client h2 connections (`for _ in 0..4 { clients.push(h2_connect(proxy_addr).await) }`), then asserts on the origin counters:

- `assert_eq!(after_first.backend_connections_opened, 400, "with an empty pool the whole first wave dials one connection each")` — `./eqproxy-net/tests/e2e_http2.rs:737-740`
- `assert_eq!(origin_after_first, 400, "the origin accepted exactly the connections the proxy dialled")`

That second assertion only holds if the origin's accept queue absorbs a simultaneous burst of 400 dials. With a smaller backlog the kernel would drop SYNs, `origin_connections` would land under 400, and the "no churn" premise would be untestable — hence the backlog must be at least 400, and it is set on the origin side, not on the proxy side.

**Which backlog is *not* the one you want.** The proxy's own listener backlog is a positional argument in the `ResolvedListener::new(...)` test helpers, and it is hard-coded to `64` in every e2e helper: `./eqproxy-net/tests/e2e_sni.rs:59-73` (`base_listener`), `./eqproxy-net/tests/e2e_phase2b.rs:109-123`, `./eqproxy-net/tests/e2e_balancer.rs:153-167` (`http_listener`), `./eqproxy-net/tests/e2e_resilience.rs:218-232`, `./eqproxy-net/tests/e2e_limits.rs:43-57`, `./eqproxy-net/tests/e2e_backend_h2.rs:1043-1056`, `./eqproxy-net/tests/e2e_ws_h2.rs:48-61`. The `64` sits between `ProxyMode` and the first `Duration`. That is the front-door backlog (only 4 client connections arrive), not the origin backlog.
